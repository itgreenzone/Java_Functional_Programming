Why FP in Java? · my notes L01

One rule all lesson long: "a transaction is high value when amount > 1,000.00"

1 · HOW vs WHAT

HOW (imperative)

I write the loop, the if,
and a mutable total.
for… if… total = total.add(…)

WHAT (declarative)

I state the recipe:
filter debits → amounts → add up.
.filter .map .reduce

Both print 16692.44 → same answer, but WHAT reads like the requirement. A loop still runs, the library owns it.

2 · Java = OO + FP features

NOT pure FP like Haskell:

  • data is mutable by default
  • side effects allowed anywhere
  • no tail-call optimisation

→ functional style is a discipline I choose.

3 · Behaviour parameterisation = the code shrinks

t -> t.amount().compareTo(THRESHOLD) > 0  works with the OLD TransactionFilter because it has exactly 1 abstract method. All steps → the same 11 transactions.

5 · Laziness = a conveyor belt

nothing moves until someone at the end pulls (the terminal operation)
peek() trace

filter T001 ✗
filter T002 ✗
filter T003 → map T003
filter T004 → map T004
= [T003, T004]

vertical, not horizontal: each element goes through ALL steps before the next one starts (loop fusion).

short-circuit: limit(2) found 2 high-value txns after looking at only 19 of 60.

peek = debugging only, never business logic.
