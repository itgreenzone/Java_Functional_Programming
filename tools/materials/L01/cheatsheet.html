Why Functional Programming in Java

Java 8 → Java 21 · shared dataset: 10 customers,
15 accounts, 60 transactions

Key rules

  1. Declarative = WHAT, imperative = HOW. Streams state the result; the library owns the loop.
  2. Java is OO with functional features (since Java 8), not a pure FP language: mutable by default, side effects allowed.
  3. Behaviour parameterisation: write the loop once, pass the rule. Strategy class → anonymous class → lambda.
  4. Any interface with one abstract method accepts a lambda, even one written before Java 8 (target typing).
  5. Pure function: same input → same output, no side effects.
  6. Streams are lazy: nothing runs until a terminal op (toList, count, reduce…). Elements flow one at a time.
  7. Money: BigDecimal, scale 2, RoundingMode.HALF_UP. Never double.

Canonical snippets

1 · Imperative vs declarative Java 8
// HOW: loop + mutable total
BigDecimal total = BigDecimal.ZERO;
for (Transaction t : txns) {
    if (t.type() == TxnType.DEBIT) {
        total = total.add(t.amount());
    }
}
// WHAT: rule + result            -> 16692.44
txns.stream()
    .filter(t -> t.type() == TxnType.DEBIT)
    .map(Transaction::amount)
    .reduce(BigDecimal.ZERO, BigDecimal::add);
2 · Anonymous class → lambda (same old interface)
filter(txns, new TransactionFilter() { // 6 lines
    public boolean matches(Transaction t) {
        return t.amount()
                .compareTo(THRESHOLD) > 0;
    }
});
// lambda: 1 line, same result (11 txns)
filter(txns,
    t -> t.amount().compareTo(THRESHOLD) > 0);

Do / Don't

✔ Do

  • Keep lambdas short; name rules
  • Prefer method references when clearer
  • Immutable data: records, List.of, toList()
  • One stream op per line

✘ Don't

  • Fill an outside list in forEach
  • Put logic in peek (debug only)
  • Expect output without a terminal op
  • Turn every loop into a stream
